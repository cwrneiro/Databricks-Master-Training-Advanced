1.2 - Job e pipeline

Nesta parte, você roda o job em dev, vê ele falhar, corrige o pipeline e promove o bundle para prod.

Passo 7: Rodar o job

Lakeflow

  1. No painel Deployments, na lista Bundle resources, passe o mouse em cima do job autorizacoes_<aluno>
  2. Clique no botão "play" (Run job)

Passo 8: Explorar a execução

  1. Clique no nome do Job na lista Bundle resources para abrí-lo. Isso abrirá uma nova aba, mantenha a aba do bundle aberta
  2. Aguarde o término da execução. Você notará que a task validar fica vermelha
  3. Clique na task validar, e veja o erro:
AssertionError: A silver tem X linhas para Y autorizações: uma linha por evento, não por autorização. ...

A task validar falha pois o número de linhas da tabela é diferente do número de IDs distintos, existem duplicatas. Vamos explorar a pipeline.

  1. Volte à interface do Job
  2. Clique na pipeline
  3. No grafo, clique em bronze_autorizacao_eventos
  4. Note que existem expectations, e pelo menos uma delas falhou

Passo 9: Explorar a definição da Pipeline

Auto Loader e Expectations

Vamos entender como é feita a definição do Auto Loader e das Expectations

  1. Volte à aba com a interface do bundle
  2. Navegue até src/pipeline/ e clique em bronze.py
  3. Note as seguintes definições:
    • @dp.expect_all(REGRAS), na qual REGRAS é um dicionário com as nossas Expectations
    • spark.readStream.format("cloudFiles"), declarando o Auto Loader lendo JSONs de um Volume

Agora vamos tratar o problema da duplicidade de registros.

Passo 10: Trocar a silver por AUTO CDC

MERGE e Change Data Feed

O AUTO CDC faz o MERGE de cada lote por você: deduplica, aplica os eventos na ordem de event_ts (mesmo os atrasados) e mantém uma linha por autorizacao_id.

  1. Navegue até src/pipeline/ e clique em silver.py

  1. Apague o bloco @dp.table(...) def silver_autorizacao_status() inteiro e cole no lugar: 
    dp.create_streaming_table(
    name="silver_autorizacao_status",
    comment="Status atual de cada autorização.",
    table_properties={"delta.enableChangeDataFeed": "true"},
)
dp.create_auto_cdc_flow(
    target="silver_autorizacao_status",
    source="silver_autorizacao_eventos",
    keys=["autorizacao_id"],
    sequence_by="event_ts",
    stored_as_scd_type=1,
)

Passo 11: Rodar de novo em dev, com full refresh

Trocar o tipo de flow (de append para AUTO CDC) exige recalcular a silver do zero, porque ela ainda guarda as linhas do run anterior.

  1. Abra o pipeline clicando em seu nome na lista de Bundle resources
  2. Clique na seta ao lado de Run pipeline
  3. Clique em Run pipeline with full table refresh

  1. Volte interface do bundle e rode o Job novamente clicando em Run job
  2. Clique no nome do Job para abrí-lo e clique na última execução

A task validar fica verde.

👉 Resultado esperado:

Não precisa de novo deploy. Em dev, o pipeline e o job leem o código direto da sua Git folder. Novo deploy em dev só quando você muda um YAML.

⚠️ Sem o full refresh, o pipeline termina sem erro, mas a silver continua com as linhas antigas e a validar falha de novo.

Passo 12: Deploy em prod

  1. No painel Deployments, troque o target para prod
  2. Clique em Deploy

Repare que agora os nomes vêm sem prefixo: o schema é academydb.<aluno>, e o job e o pipeline se chamam autorizacoes_<aluno>.

⚠️ Em prod, o deploy copia o código para .bundle/vida_saude/prod/files, e o job roda essa cópia. Uma mudança de código só vale em prod depois de um novo deploy em prod.

Passo 13: Rodar o job em prod

  1. Na lista Bundle resources, clique em Run job no job de prod.
  2. Abra o Job clicando no nome dele da lista
  3. Veja que agora ele passa de primeira, porque o código já está corrigido

Em prod, o schedule está ligado: o job roda sozinho a cada 10 min.

Daqui em diante, o workshop segue em prod, para economizar tempo. No dia a dia, desenvolva sempre em dev e só promova para prod depois de confirmar que funciona.

Passo 14: Ver a fila de runs

No autorizacoes.job.yml, o job tem max_concurrent_runs: 1 e queue.enabled: true.

  1. Abra a página do job de prod
  2. Clique em Run now duas vezes seguidas

Repare que o segundo run fica Queued até o primeiro terminar, em vez de rodar junto ou ser descartado.

Bônus: Explorando os tipos de Job triggers

  1. Navegue até Jobs & Pipelines usando o menu lateral esquerdo
  2. Procure e selecione o job edia_gerador_eventos
  3. Nas configurações à direita, abaixo de Schedules & Triggers, clique em Edit trigger
  4. Clique no dropdown Trigger type
  5. Note os diferentes tipos de trigger:
    • Scheduled
    • File arrival
    • Table update
    • Continuous

🎯 Desafio: histórico de status (SCD2)

Crie a silver_autorizacao_historico, com uma linha por mudança de status de cada autorização (__START_AT e __END_AT marcam a vigência).

Dica: é o mesmo AUTO CDC, com stored_as_scd_type=2. Como é uma tabela nova, basta um Run job, sem full refresh.

👉 Solução

No fim de src/pipeline/silver.py, adicione:

dp.create_streaming_table(
    name="silver_autorizacao_historico",
    comment="Histórico de status de cada autorização (SCD2).",
)
dp.create_auto_cdc_flow(
    target="silver_autorizacao_historico",
    source="silver_autorizacao_eventos",
    keys=["autorizacao_id"],
    sequence_by="event_ts",
    stored_as_scd_type=2,
    track_history_column_list=["status"],
)

Para conferir, rode as duas queries:

-- Visão histórica do registro (SCD Type 2)
SELECT *
FROM academydb.<aluno>.silver_autorizacao_historico
ORDER BY autorizacao_id, event_ts
LIMIT 100;

-- Registros históricos X vigentes
SELECT count(*) AS historico, count_if(__END_AT IS NULL) AS vigente
FROM academydb.<aluno>.silver_autorizacao_historico;

O status atual de cada autorização é a linha com __END_AT IS NULL, então vigente é igual ao número de linhas da silver_autorizacao_status.

💡 Por que SDP é o padrão

Em Structured Streaming "na mão" (os comentários abaixo de cada bloco do pipeline), você escolhe e guarda os checkpoints, escreve o MERGE, cuida da idempotência, ordena as dependências entre tabelas e reprocessa tudo quando algo muda.

No pipeline declarativo, você descreve o que cada tabela é, e a plataforma cuida do como: checkpoints, ordem de execução, retries, qualidade de dados (expectations) e full refresh. O código fica menor, e o que sobra é regra de negócio.

Structured Streaming continua por baixo, e você recorre a ele quando precisa de algo que o pipeline não oferece.

💡 O mesmo pelo CLI, e num CI

Cada botão do painel Deployments tem um comando equivalente no CLI do Databricks. É o que roda num pipeline de CI/CD, onde ninguém clica em Deploy:

cd "01 - Pipeline e bundle"
databricks bundle validate -t prod             # confere o YAML e resolve as variáveis, sem criar nada
databricks bundle deploy -t dev                # o Deploy do painel, no target dev
databricks bundle run -t dev autorizacoes_job  # o Run job
databricks bundle deploy -t prod --var aluno=acarneiro  # --var troca uma variável sem editar o YAML

O nome depois de run é a chave do recurso no YAML (autorizacoes_job), não o nome que aparece no workspace.

Em prod, o job e o pipeline rodam como quem fez o deploy: hoje, você. No dia a dia, isso quebra no primeiro dia de férias. Por isso, o target prod de um projeto real declara um service principal (SP), uma identidade que não é de nenhuma pessoa:

  prod:
    mode: production
    run_as:
      service_principal_name: 00000000-0000-0000-0000-000000000000 # application ID do SP

E o deploy sai das mãos das pessoas: um merge na branch principal dispara o CI, que se autentica como o SP e roda o mesmo deploy -t prod. Um exemplo com GitHub Actions:

on:
  push:
    branches: [main]
jobs:
  deploy:
    runs-on: ubuntu-latest
    env:
      DATABRICKS_HOST: ${{ secrets.DATABRICKS_HOST }}
      DATABRICKS_CLIENT_ID: ${{ secrets.DATABRICKS_CLIENT_ID }}         # application ID do SP
      DATABRICKS_CLIENT_SECRET: ${{ secrets.DATABRICKS_CLIENT_SECRET }} # secret OAuth do SP
    defaults:
      run:
        working-directory: 01 - Pipeline e bundle
    steps:
      - uses: actions/checkout@v4
      - uses: databricks/setup-cli@main
      - run: databricks bundle validate -t prod
      - run: databricks bundle deploy -t prod
